# 竞赛文档去 AI 味与写作

把目标设为“像真实项目团队写出的正式材料”，而不是“像聊天的人说话”。优先保证事实、证据、技术精度和评审逻辑，再处理语言自然度。

## 核心原则

1. 先保真，再润色。不得为了句子顺滑改变数据、结论、指标、公式、引用、技术关系或项目边界。
2. 以证据替代形容词。优先写“做了什么、怎么做、结果是什么”，少写“先进、领先、全面、深度、显著、赋能”等空泛评价。
3. 以具体动作替代宏大立意。项目价值要落到对象、场景、流程、指标、成果或实际问题上。
4. 正式但不官腔。技术文档保持客观、克制；答辩稿和视频稿允许更口语，但仍要准确。
5. 不为“像人”而故意加入跑题、情绪、第一人称或网络口语。除非文体本身需要。
6. 不把单个词判定为 AI 痕迹。只有当套话、结构、节奏和抽象表达成组出现时，才视为需要改写。
7. 文本内容与版式同等受约束。处理 Word 文档时，必须同时检查摘要编号、图表题注位置、页眉页脚、页码体系、表格分页和段落对齐，不能只改正文措辞。

## 执行流程

### 1. 判断任务类型

先判断用户需要哪一种：

- **新写**：根据资料生成竞赛材料。
- **重写**：保留原意、事实和结构，降低 AI 味并提高专业度。
- **审校**：指出问题并给出修改稿。
- **评审导向优化**：围绕问题、创新、证据、应用、团队或成果重新组织内容。

如果用户已经给出足够资料，直接执行，不要为了形式反复追问。

### 2. 锁定不可擅改的信息

在改写前，内部标记以下内容为“事实锁”：

- 项目名称、模块名称、专有名词；
- 数字、百分比、时间、版本、实验条件；
- 专利、论文、奖项、软著、客户、合作单位、部署数量等资质信息；
- 引用来源、参考文献、公式、代码、命令、接口名；
- 已验证的架构关系、流程顺序、测试结论。

除非用户明确要求，否则不得新增、猜测或放大这些内容。没有证据时，不写“行业领先”“国内首创”“填补空白”“已广泛应用”“显著提升”等结论。

### 3. 扫描 AI 写作模式

需要系统审查时，读取：

- `references/humanizer-rules.md`
- `references/vibehub-rules.md`

重点处理：夸大意义、宣传腔、模糊归因、假深度、机械三段式、否定式排比、过多连接词、AI 高频抽象词、固定开场结尾、夸张比喻、每句话都分点等。

**强制直述规则：**

- 禁止使用“不是 X，而是 Y”“不以 X，而是 Y”“并非 X，而是 Y”“不是为了 X，而是为了 Y”等先否定后转折的模板句式。
- 不要为了强调观点先设置一个被否定的命题。直接写结论、动作、原因或结果。
- 禁止使用中文双引号作为强调手段；竞赛正文、标题、题注、表格说明和答辩文案中原则上不出现中文双引号。
- 原文中的产品名、模块名、术语名不靠引号突出，使用正常文本或必要的专名格式。文献、政策、标准、文件名称优先使用书名号。
- 必须保留的逐字引文仅在引用规范明确要求时保留；其余内容改为转述。

### 4. 按竞赛逻辑重写

需要写申报书、总结报告、项目介绍、答辩稿等材料时，读取 `references/competition-writing-guide.md`。

优先采用以下信息链：

**问题/需求 → 现有不足 → 团队采取的技术或实践动作 → 可核验依据 → 结果/价值 → 适用边界**

并不是每段都必须机械写满六项。根据章节选择最需要的信息，但避免只写价值判断而没有动作或证据。

### 5. 执行项目术语规范

涉及“可信卫士”项目或用户要求沿用该项目规范时，读取 `references/trustguard-conventions.md`。

术语统一优先级高于语言变化。不要为了“避免重复”而给同一模块随意换名字。

### 6. 执行 Word 版式规范

处理项目申报书、设计/开发/测试文档、总结报告等 `.docx` 文件时，读取 `references/trustguard-conventions.md` 中“Word 文档版式规范（强制）”。至少落实：

- 摘要标题不设章节编号；
- 一级标题使用 `一、`、`二、` 等中文序号；二级标题使用 `1.1`、`1.2`，三级标题使用 `1.1.1`、`1.1.2`，必要时继续按阿拉伯数字层级编号；
- 标题命名优先控制在约 4–6 个汉字，按内容自然调整，不强行全部四字化；避免使用“XX与XX”式并列标题，标题直接概括本节核心内容；
- 正文中文统一宋体，英文/英文缩写统一 Times New Roman，正文默认小四（12 pt）；标题、表名、图名同样使用黑色、小四，中文宋体，英文字符 Times New Roman；
- 正文关键结论、关键数据、创新点、关键技术机制和阶段成果可选择性加粗，避免整段或高密度加粗；
- 表名置于表格前，图名置于图片后；图表题注统一为 `表 X-Y 表名` / `图 X-Y 图名`；
- 表格与图片本体水平居中；图表题注水平居中；
- 页眉、页脚内容居中；
- 目录页使用罗马数字页码，正文另起节并从阿拉伯数字 1 重新编号；
- 调整表格版式，避免表名孤立在上一页；能单页容纳的表格应与表名保持在同一页；
- 正文段落采用两端对齐（Justify）。

生成或修改 `.docx` 后必须做版式复核；如果有可用的 Word/DOCX 渲染能力，应渲染检查页码、题注与分页效果，而不是只检查文本结构。

### 7. 二次审校

完成初稿后再检查一遍：

- 是否出现没有依据的拔高、领先性、规模或效果；
- 是否连续出现“此外、同时、值得注意的是、进一步、从而、有效”等连接词；
- 是否出现先否定再转折的模板句式，例如“不是 X，而是 Y”“不以 X，而是 Y”“并非 X，而是 Y”；发现后必须改为直接陈述；
- 是否出现中文双引号；除引用规范强制要求的逐字引文外，应改为直接陈述、转述或使用书名号等合适格式；
- 是否多次使用“不仅……更……”等模板；
- 是否三项、三段、三层结构过密；
- 是否把普通技术动作写成“赋能、重塑、引领、构建生态、形成闭环”；
- 是否一个自然段中全是相同长度、相同句式；
- 是否把本可直接说明的内容拆成过多编号；
- 是否遗漏关键证据、数据来源、实验条件或限定条件；
- 是否改坏术语、缩写、表格字段、公式或代码；
- 摘要是否误加章节编号；
- 一级标题是否使用 `一、`、`二、`，二级/三级标题是否使用 `1.1`、`1.1.1` 等层级编号；
- 标题是否简洁、贴合段落内容，是否机械四字化或出现不必要的“XX与XX”并列结构；
- 中文是否统一宋体、英文是否统一 Times New Roman、正文是否小四（12 pt）；标题和图表题注是否为黑色、小四并正确处理中英文字体；
- 重点加粗是否只用于关键结论、数据、创新点、技术机制和成果，是否存在整段滥用加粗；
- 表名是否位于表格前、图名是否位于图片后，且题注是否符合 `表 X-Y 表名` / `图 X-Y 图名`；
- 图片、表格及图表题注是否水平居中；
- 页眉页脚是否居中；目录页是否使用罗马数字页码，正文是否从阿拉伯数字 1 重新编号；
- 是否存在表名落在上一页而表格从下一页开始的情况；
- 正文段落是否统一为两端对齐。

如仍存在明显模式，继续改写，不要在第一次润色后停止。

## 不同文体的语气

### 申报书 / 商业计划书

写得清楚、紧凑、有证据。可以强调价值，但价值必须能回扣需求、用户、技术、市场或成果。

### 设计 / 开发 / 测试文档

优先技术准确和可复现。少用修辞，避免“展示了强大能力”“充分体现”等评价句。描述组件、接口、流程、部署和测试时使用具体动词。

### 总结报告

避免把每一节结尾都写成升华。总结“完成了什么、验证了什么、还存在哪些边界”，比“为未来发展奠定坚实基础”更有效。

### 答辩稿 / 演示视频稿

允许短句和自然转折，可以用“我们”，但不要使用客服腔、主持人套话、夸张比喻或连续口号。讲解顺序优先跟随屏幕操作和证据出现顺序。

### PPT 文案

压缩句子而不是堆关键词。标题优先表达判断或信息，不要每页都用“赋能、重构、引领、革新”。正文只保留能支撑页面主旨的信息。

## 输出方式

根据用户要求选择最简洁的交付方式：

- 用户要求“直接改/重写”时：优先直接给可用成稿，不附长篇方法说明。
- 用户要求“找 AI 味/审校”时：默认用 `原句 | 问题 | 修改建议 | 修改后` 表格；长文只列有问题的代表性句子，另给完整修订稿（如用户需要）。
- 用户要求“写一节/一段”时：给完成稿，不把分析过程写进正文。
- 用户明确要求保留结构、标题、字数或格式时：严格遵守。

## 竞赛材料的事实纪律

不得自行虚构：

- 市场规模、增长率、用户数量、订单、收入；
- 测试准确率、性能提升百分比、节省时间；
- 专利、软著、论文、竞赛奖项；
- 企业合作、客户评价、政府背书；
- 已部署、已落地、已商业化等状态。

资料不足时，采用克制表述，或在需要用户补充的位置使用明确占位符，如 `[补充实测数据]`，不要用模糊权威替代证据。
