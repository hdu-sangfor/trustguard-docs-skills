# 互联网+/创新大赛/挑战杯文档写作指南

本指南用于提高竞赛材料的评审可读性，不替代当届官方评审规则。若用户明确要求“按 2026/某届/某赛道评分标准优化”，应优先核对当届官方文件，再把具体评分点映射到文档。

## 一、评委真正需要快速判断的内容

无论是创新创业类还是科技作品类，文档都应尽快回答：

1. **问题是否真实**：对象是谁，场景是什么，现有方案为什么不够。
2. **项目是否真的做了**：团队完成了哪些调研、研发、实验、部署或验证。
3. **创新在哪里**：与已有方法相比，新增了什么机制、能力、流程或应用方式。
4. **证据是否够硬**：有没有实验数据、对比、代码、原型、用户验证、成果材料或可复现过程。
5. **价值是否成立**：技术价值、应用价值、产业价值或社会价值能否从证据中推出。
6. **团队是否匹配**：团队成员是否真实参与，能力结构与项目任务是否对应。

挑战杯科技作品常强调科学性、先进性、现实意义，以及应用价值和转化前景；创新大赛近年的高教主赛道则持续关注学生成长、项目创新、产业/社会价值和团队协作。写作时不要把这些词当口号，要把它们转化成可验证内容。

## 二、证据优先级

从强到弱大致为：

**实测数据/实验记录 > 可复现实物或系统 > 真实用户/场景验证 > 第三方材料 > 代码与工程记录 > 明确调研数据 > 团队判断 > 宣传性形容词**

不要用最弱的表达替代本来已经有的强证据。例如已经有测试表，就不要只写“系统性能显著提升”。

## 三、常用章节怎么写

### 1. 摘要

摘要建议覆盖四件事：

- 背景问题；
- 项目做法；
- 核心创新；
- 已取得的结果或当前状态。

不要在摘要里塞满“赋能、引领、突破、生态、闭环”。摘要应让陌生评委读完后能准确复述项目。

### 2. 项目背景 / 痛点

优先写具体场景和矛盾：

- 谁在什么情况下遇到什么问题；
- 现有流程在哪一步成本高、效率低、风险高或能力不足；
- 团队如何发现这个问题：调研、访谈、实验、实习、行业资料、真实需求。

不要只写“随着数字化快速发展，网络安全问题日益严峻”。这种句子可以被任何项目复用，信息量太低。

### 3. 需求分析

把需求写成可以验证的能力，而不是口号。

弱：需要构建智能高效的一体化平台。

强：需要同时支持任务编排、运行过程可观测、知识检索、结果留痕，并允许不同安全任务复用统一工具接口。

### 4. 方案 / 技术路线

按数据流、调用链或工作流程写。每个关键模块说明：输入、处理、输出、与其他模块的关系。

不要把架构图翻译成一串“通过……实现……”；应解释为什么这样拆分、解决了什么工程问题。

### 5. 创新点

创新点必须可比较。推荐使用：

**现有做法/限制 → 本项目做法 → 技术差异 → 验证结果或实际收益**

避免：

- “首次提出”但没有检索或证明；
- 把用了热门技术本身当创新；
- 把多个普通功能组合后直接称为“体系创新”；
- 每个创新点都写成三段口号。

如果创新主要来自工程整合，应如实写成“工程创新、流程创新、应用创新”，不要硬包装成基础理论突破。

### 6. 研发过程 / 开发周期

写真实工程过程：

- 如何拆任务；
- 关键版本或阶段；
- 遇到什么技术问题；
- 如何验证和修复；
- Git 提交、PR、Issue、测试、部署等记录能说明什么。

不要把“使用 Git、Docker、前后端分离”本身当亮点；重点是这些工具如何支撑协作和交付。

### 7. 测试与验证

必须写清：

- 测试对象；
- 测试环境/前提；
- 测试步骤；
- 指标定义；
- 结果；
- 失败条件或限制。

如果只有功能验证，不要写成性能测试；如果样本量不足，不要推导“普遍有效”。

### 8. 应用与落地

严格区分：

- 已完成原型；
- 已内部试用；
- 已在真实场景验证；
- 已部署；
- 已产生订单/收入；
- 仅计划推进。

不要把“可应用于”写成“已广泛应用于”。

### 9. 市场 / 产业分析

有可靠来源时写市场规模、竞争格局和趋势；没有来源时宁可少写。

竞品比较要选择相同维度，避免“我们全是√、竞品全是×”。对方优势也可如实写，反而提高可信度。

### 10. 团队介绍

不写“团队成员优势互补、凝聚力强”这种无证据评价。写成员职责与实际贡献：谁负责算法、后端、前端、测试、产品、调研、商业分析，以及对应成果。

### 11. 社会价值 / 产业价值

采用“对象 + 机制 + 可观察结果”的写法。

例如不是“推动网络安全行业高质量发展”，而是说明项目减少了哪个环节的人工工作、降低了哪类门槛、改善了哪类安全流程；若已有数据，再给结果。

### 12. 总结与展望

总结已完成事项和已经验证的结论。展望写下一步具体动作，例如：

- 扩充某类数据；
- 增加某类工具适配；
- 在某环境做压力测试；
- 将人工审核节点引入某流程；
- 开展真实用户试用。

避免“持续迭代、不断优化、拓展更多场景、打造行业生态”这种无法检查的结尾。

## 四、不同比赛侧重点的写作迁移

### 创新大赛 / 原互联网+风格

材料通常需要同时讲清技术、用户、产业/社会价值和团队成长。技术写得再强，也不要完全忽略需求、落地和团队；商业部分也不能脱离真实研发状态。

### 挑战杯课外学术科技作品风格

更强调科学问题、技术先进性、现实意义、实验与作品本身。减少商业计划书式包装，增加方法、实验、对比和作品可验证性。

### 创业计划类挑战杯

更重视需求、商业逻辑、团队、资源和落地。技术创新要讲清，但不要把整份材料写成开发文档。

## 五、标题写法

标题优先传达信息，不追求口号。正式 Word 文档中的标题还必须遵守 `references/trustguard-conventions.md` 的编号和字体规则。

### 标题命名原则

- 标题应直接概括本节内容，优先使用清楚的名词性或动作性短语。
- 通常控制在约 **4–6 个汉字**最利于扫读，但根据技术术语和内容自然调整，不把字数当成硬指标。
- 不要为了“整齐”把所有标题都改成四个字；连续十几个四字标题会形成明显模板感。
- 避免把“XX与XX”作为默认结构，如“设计与实现”“问题与挑战”“部署与运维”。能确定一个核心主题时，就用单中心标题。
- 不写“赋能、引领、重塑、智启、共创未来”等宣传口号。
- 标题长度应服从信息量：内容单一时可短，涉及明确技术对象时可适度加长。

较弱：
- 智启未来：打造下一代安全新生态
- 多维赋能，构筑可信智能新底座
- 设计与实现
- 问题与挑战

更强：
- 系统架构
- 任务编排
- 告警研判流程
- 知识检索机制
- 安全工具接入
- 部署流程

对于必须说明具体技术对象的章节，可自然超过 6 个字，例如“RAG 知识检索流程”“XDR 告警研判机制”，不要为了凑字数删掉关键对象。

如比赛材料需要品牌化主标题，可采用“品牌名 + 一句清晰副标题”，但副标题仍应说明项目是什么。

## 六、段落写法

一段通常围绕一个主要判断展开。建议优先使用：

**结论句 + 2～4 句事实/动作/证据**

不要强迫每段都遵循相同长度，也不要每段末尾升华。

## 七、数据与表格

- 表格适合参数、对比、测试结果、里程碑、功能清单。
- 正文不要逐格复述表格；只解释关键差异和结论。
- 数字必须保持单位、条件和口径一致。
- 没有基线时，不写“提升 X%”。

## 八、真实性红线

创新大赛 2026 通知明确要求对项目资格、成员实质性贡献，以及科技成果、知识产权、财务、运营、荣誉奖项等真实性与合规性进行审核。竞赛文档润色绝不能把“计划、原型、意向、测试”改写成“已落地、已合作、已获奖、已商业化”。

## 九、当用户要求“按评分标准优化”时

执行：

1. 确认比赛名称、年份、赛道/组别；
2. 如可联网，优先查看当届官方规则；
3. 建立 `评分点 | 当前证据 | 文档位置 | 缺口 | 修改动作` 映射；
4. 只优化表达和组织，不补造证据；
5. 对缺口明确标注需要团队补充的材料。

## 十、Word 文档版式检查

当交付物是项目申报书、设计文档、开发文档、测试文档或总结报告等 Word 文档时，除内容审校外还要执行版式检查。具体格式以 `references/trustguard-conventions.md` 中的“Word 文档版式规范（强制）”为准。

重点检查：摘要是否无章节编号；标题编号是否采用一级 `一、`、二级 `1.1`、三级 `1.1.1`；标题名称是否简洁且贴合内容；中文/英文字体、字号和黑色题注是否统一；图片、表格和图表题注是否居中；目录与正文是否分节编号；页眉页脚是否居中；表名是否与表格同页；正文是否两端对齐；重点加粗是否克制且真正突出评审关键信息。不要因为“文字已经改完”而跳过版式验证。



## 强制直述与引号规则

- 竞赛材料优先直接陈述事实、动作、原因、结果和判断。
- 禁止使用先否定后转折的强调模板，包括“不是 X，而是 Y”“不以 X，而是 Y”“并非 X，而是 Y”“不是为了 X，而是为了 Y”。
- 遇到此类句子时，删除前置否定项，直接保留真正需要表达的结论，并补充事实或证据。
- 正文、标题、题注、表格说明、PPT 文案和答辩稿原则上不使用中文双引号作强调。
- 文件、政策、标准、书籍名称使用书名号；产品、模块、技术术语直接书写，不套引号。
- 除引用规范要求的逐字引文外，引用内容优先改为转述，保持事实含义与来源不变。
